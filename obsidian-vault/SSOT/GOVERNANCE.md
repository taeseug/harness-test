### RACI 범례

- **R**esponsible: 작업 실행 (문서 작성, 변경 구현)
- **A**ccountable: 최종 책임 (승인, 완료 확인)
- **C**onsulted: 의견 수렴 (리뷰, 피드백)
- **I**nformed: 정보 전달 (결과 공지)

### 예제: 모델 선택 변경

```
RACI Matrix:
                       R  A  C  I
모델 선택 Owner      ✅ 
기술리더             ✅ ✅
ML팀                       ✅
개발팀                      ✅ ✅
인프라팀                     ✅ ✅

= Owner가 변경 구현, 기술리더가 승인,
  ML/개발/인프라가 검토/정보 받음
```

## 🔄 의사결정 프로세스

### 의사결정 분류

#### 1. Type A: 긴급 결정 (24시간 내)
- SSOT 구현상 critical issue
- 프로덕션 장애 대응
- 보안 문제

**승인 프로세스**:
1. Owner 제안
2. 기술리더 즉시 승인
3. 팀 공지 (비동기)

**예제**:
```
문제: 모델 A가 예상 성능 50% 미만 달성
→ Owner가 즉시 대체 모델 제안
→ 기술리더 승인
→ 팀에 공지 + ADR 작성
```

#### 2. Type B: 일반 결정 (1-2주)
- SSOT 내용 추가/수정
- 가이드라인 업데이트
- 프로세스 개선

**승인 프로세스**:
1. Owner가 ADR 초안 작성
2. 관련 팀에 2-3일 검토 요청
3. 기술리더 승인
4. SSOT 업데이트 + 회의록 기록

**예제**:
```
제안: 프롬프트 엔지니어링 가이드 v2 작성
↓
ADR 문서 작성 (Owner)
↓
검토 기간 3일 (팀의 의견)
↓
기술리더 승인
↓
SSOT 업데이트 + 팀 공지
```

#### 3. Type C: 경미한 업데이트 (즉시)
- 문서 오류 수정
- 예제 추가
- 링크 업데이트

**승인 프로세스**:
1. Owner가 직접 수정
2. 변경 이력에 기록
3. Slack에 공지 (정보용)

## 📝 변경 관리

### 변경 신청 프로세스

```
1️⃣ 변경 식별
   └─ 팀 멤버가 문제/아이디어 발견

2️⃣ 변경 제안
   └─ Owner에게 Slack/Email로 제안

3️⃣ 우선순위 분류
   ├─ Type A (긴급) → 즉시
   ├─ Type B (일반) → 1-2주
   └─ Type C (경미) → 다음 정기 검토

4️⃣ ADR 작성 (Type A/B만)
   └─ ADR 템플릿 사용: [[Decisions/_decision-template]]

5️⃣ 검토 및 승인
   └─ 기술리더 최종 승인

6️⃣ 문서 업데이트
   └─ [[SSOT.md]] + 구체적 문서

7️⃣ 팀 공지
   └─ 회의 또는 Slack 공지

8️⃣ 변경 이력 기록
   └─ SSOT의 변경 이력 섹션 업데이트
```

### 변경 신청 템플릿

```markdown
**변경 유형**: Type [A/B/C]
**제안자**: [이름]
**날짜**: [YYYY-MM-DD]
**영향받는 SSOT**: [[model-selection]], ...

**현재 상태**:
- 

**문제점**:
- 

**제안하는 변경**:
- 

**예상 효과**:
- 

**관련 ADR**: [[ADR-XXX]] (있으면)
```

### 버전 관리

SSOT 버전 형식: **v MAJOR.MINOR.PATCH**

```
v1.0.0 → v1.0.1 (문서 오류 수정)
v1.0.1 → v1.1.0 (새 가이드라인 추가)
v1.1.0 → v2.0.0 (패러다임 변경)
```

**변경 이력 예**:

| 버전 | 날짜 | 변경사항 | Owner | 상태 |
|------|------|---------|-------|------|
| v1.0.0 | 2026-08-10 | 초기 구조 수립 | [이름1] | ✅ |
| v1.0.1 | 2026-08-12 | 오류 수정 | [이름1] | ✅ |
| v1.1.0 | 2026-08-20 | 추론 최적화 가이드 추가 | [이름3] | ✅ |

## 🚀 배포 절차

### 배포 전 체크리스트

SSOT를 변경하기 전에:

- [ ] 관련 팀의 의견 수렴 (2-3일)
- [ ] 예제 및 코드가 실행 가능한가?
- [ ] 다른 SSOT 문서와 모순 없는가?
- [ ] 변경 이력 업데이트?
- [ ] 기술리더 승인?
- [ ] 팀에 공지할 메시지 준비?

### 배포 (Type B 기준)

```
월요일: ADR 초안 제출
화-수: 팀 검토 (코멘트/피드백)
목요일: 기술리더 승인
금요일: SSOT 업데이트 + 팀 공지

🎯 1주 사이클
```

### 롤백 절차

SSOT 변경 후 문제 발견시:

```
1. 즉시 회귀: 이전 버전으로 복원
2. 근본 원인 분석: 왜 문제가 발생했는가?
3. 수정: 문제 해결
4. 재배포: 수정된 버전 배포
5. 포스트모템: 실수 방지를 위해 기록
```

