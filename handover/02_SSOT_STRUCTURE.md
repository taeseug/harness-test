## 📌 SSOT의 6가지 핵심 규칙

### 1️⃣ 모델 선택 (📌 선택하기)

**언제 사용?** - 새로운 작업이 필요할 때

```
┌─ Haiku 4.5
│  • 경량 작업: 분류, 간단한 요약
│  • 특징: 빠름 (100ms), 저비용
│  └─ 예: 감정분석, 레이블링
│
├─ Sonnet 5
│  • 중간 난도: 자유형 생성, 복잡 요약
│  • 특징: 균형잡힘 (중속, 중비용)
│  └─ 예: 글쓰기, 코드 생성, 요약
│
└─ Opus 5
   • 복잡 추론: 논리, 계획, 다단계 추론
   • 특징: 강력 (느림, 고비용)
   └─ 예: 복잡한 문제 풀이, 거시적 계획
```

**의사결정 트리**:
```
작업이 간단한가?     → YES → Haiku
                   → NO  → 다음으로

응답 속도가 중요한가? → YES → Sonnet
                   → NO  → 다음으로

깊은 추론이 필요한가? → YES → Opus
                   → NO  → Sonnet
```

**실제 예시**:
- ✅ 고객 이메일 분류 → Haiku (분류, 빠름)
- ✅ 고객 응답 작성 → Sonnet (생성, 품질)
- ✅ 전략 수립 → Opus (복잡 추론)

---

### 2️⃣ 프롬프트 엔지니어링 (💬 명확하게)

**4가지 원칙**:

```
1. 명확성 (Clarity)
   ❌ "좋은 요약을 만들어"
   ✅ "300자 이내로 핵심 3가지만 요약하세요"

2. 구조화 (Structure)
   ❌ 길게 설명
   ✅ 섹션으로 나누기 (배경/지시/예제/형식)

3. 맥락 최소화 (Context Efficiency)
   ❌ 쓸데없는 배경 길게
   ✅ 필요한 것만 간결하게

4. 예제 포함 (Examples)
   ❌ 명령어만
   ✅ 명령어 + 입출력 예제 2-3개
```

**체크리스트**:
- [ ] 지시가 한 문장으로 요약 가능한가?
- [ ] 입력/출력 형식이 명시되어 있는가?
- [ ] 예제가 2개 이상 있는가?
- [ ] 300토큰 이내인가?

---

### 3️⃣ 추론 전략 (🔄 빠르고 효율적으로)

**온도 설정**:
```
0.0  = 결정적 (항상 같은 답)
      └─ 사용: 분류, 구조화된 출력, 번역

0.5  = 균형
      └─ 사용: 대부분의 일반 작업

0.7  = 창의적 (다양한 답)
      └─ 사용: 창의 작업, 아이디어 생성

1.0+ = 매우 창의적
      └─ 사용: 거의 없음 (예측 불가)
```

**배치 처리**:
```
개별 호출:   지연시간 100ms × 1000개 = 100초
배치 호출:   지연시간 1초 × 1번 = 1초 (100배 빠름!)

언제 배치?   • 100개 이상 요청
            • 실시간이 아닐 때
```

**캐싱**:
```
처음:  프롬프트 + 입력 → 처리 (느림)
재사용: 캐시된 프롬프트 + 입력 → 처리 (빠름 + 저비용)

효과:  토큰 90% 절감, 속도 10배 향상
```

---

### 4️⃣ 평가 방법론 (📊 품질 측정)

**4단계 평가 레벨**:

```
L1: Rule-based (자동화 가능)
    └─ 규칙: "키워드 포함?", "길이 맞나?", "형식 올바른가?"
    └─ 속도: 매우 빠름
    └─ 정확도: 단순 규칙만

L2: Reference-based (참고 문서 비교)
    └─ 기준: "골드 표준" 답변과 비교
    └─ 점수: BLEU, ROUGE (텍스트 유사도)
    └─ 정확도: 중간 (비슷하면 맞다고 가정)

L3: LLM-as-judge (다른 LLM으로 평가)
    └─ 평가자: GPT-4 같은 강력한 모델
    └─ 기준: 자세한 체크리스트
    └─ 정확도: 높음 (인간과 유사)

L4: Human eval (직접 확인)
    └─ 방법: 사람이 직접 읽고 평가
    └─ 정확도: 가장 높음
    └─ 비용: 비쌈
```

**선택 기준**:
- 빠른 프로토타입? → L1
- 프로덕션 배포 전? → L2-L3
- 최종 품질 검증? → L4
- 지속적 모니터링? → L1-L2 (자동화)

### 5️⃣ 스케일링 법칙 (📈 성능 예측)

**성능 = (모델크기^a) × (데이터크기^b)**

```
현재:  성능 = 100점
       • 모델: Sonnet (크기 = 5)
       • 데이터: 1000개 사례

만약 데이터를 2배 늘리면?
       → 성능 ≈ 105점 (5% 향상)
       → ROI: 높음 (데이터가 저렴)

만약 모델을 Opus로 업그레이드하면?
       → 성능 ≈ 120점 (20% 향상)
       → ROI: 낮음 (모델이 비쌈)

결론: 데이터 먼저, 그 다음 모델 업그레이드
```

**실제 적용**:
```
Step 1: Haiku + 데이터 최적화
Step 2: Sonnet + 데이터 최적화  
Step 3: Opus (필요한 경우만)
```

### 6️⃣ 에러 처리 (⚠️ 안정성)

**3가지 에러 레벨**:

```
E1: 입력 검증 (사람의 실수)
    ├─ 어떤 에러? 형식 잘못, 값 누락
    ├─ 대처: 즉시 거부 (명확한 메시지)
    └─ 예: "날짜 형식을 YYYY-MM-DD로 입력하세요"

E2: 모델 한계 (모델의 한계)
    ├─ 어떤 에러? 모델이 답을 못 함
    ├─ 대처: 폴백 또는 더 강한 모델
    └─ 예: 복잡한 논리 → Sonnet → Opus로 재시도

E3: 시스템 에러 (API 장애)
    ├─ 어떤 에러? API 다운, 네트워크 문제
    ├─ 대처: 재시도 + 대기 + 알람
    └─ 예: 3초 대기 후 재시도 (최대 3회)
```

**에러 처리 체크리스트**:
```
[ ] 입력 검증 (E1)
[ ] 결과 검증 (모델 한계 감지)
[ ] 재시도 로직 (E3)
[ ] 명확한 에러 메시지
[ ] 모니터링 & 알람
```

## 🎯 SSOT의 3가지 사용 패턴

### 패턴 1: 새로운 작업 설계

```
1. 작업 특성 파악
   └─ 간단한가? 빠른가? 추론 필요한가?

2. SSOT 모델 선택 섹션 참고
   └─ Haiku / Sonnet / Opus 결정

3. 프롬프트 엔지니어링 원칙 적용
   └─ 명확성, 구조화, 예제

4. 평가 방법 선택 (L1-L4)
   └─ 단계별로 품질 검증

5. 스케일링 계획
   └─ 데이터 먼저, 그 다음 모델
```

### 패턴 2: 문제 해결

```
성능이 안 좋다?
  → [[에러 처리]] 체크
     E1 검증? → E2 모델? → E3 시스템?

응답이 느리다?
  → [[추론 전략]] 배치/캐싱 체크

비용이 높다?
  → [[모델 선택]] Haiku로 변경 가능?
  → [[스케일링]] 데이터로 개선 가능?
```

### 패턴 3: SSOT 업데이트

```
새로운 모델 출시?
  → [[모델 선택]] 섹션에 추가
  → 성능/비용 비교표 작성
  → ADR 기록

좋은 프롬프트 발견?
  → [[프롬프트 엔지니어링]] 사례로 추가
  → 팀에 공유 (회의)
```

## 💡 팁

**SSOT를 효과적으로 사용하려면:**

1. **정기적으로 읽기**
   - 월간 리뷰: 변경사항 확인 (1시간)
   - 필요시: 해당 섹션만 (5분)

   - 새로운 모델/방법? → ADR 작성
   - 실패 사례? → 이유 기록
